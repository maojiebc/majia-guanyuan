# 门店手机成绩单 V2 实践

本版延续单卡、纵向浏览的页面结构。重点是减少数据搬运、让手机上的标题与明细更一致，并把可以每天执行的确定性校验放进 ETL。离线案例见 [V2](../examples/store-mobile-scorecard-v2/README.md)，旧 [V1](part-c-store-mobile-scorecard.md) 保留。

## 数据裁剪与选店

专供层按日、门店和模块需要的粒度聚合。财务、新老客、会员、核销等保留最多70天；饭点保留16天；产品与汤底固定近7天；周期会员单独做卡号去重，不累加每日去重人数。总计19个数据视图，继续按列名识别视图而不是依赖 children 下标，不加载未展示的 RFM。

近70天没有营业额也没有订单的门店，从有效门店集合中剔除；财务、顾客订单或POS任一来源满足条件即保留。不要仅凭某一天零收入、某渠道空值或没有会员就删店。所有专供输出通过有效门店集合收窄。

筛选器顺序是分公司→门店。门店列表按固定近7天总营业额降序，再按店名稳定排序。先选分公司再求可选门店，避免旧店条件与新店条件同时进入 AND 筛选导致空白。该排序不随昨日／近30天／本月切换，也不按会员订单占比排序。

SQL 与数据依赖在 [etl/](../examples/store-mobile-scorecard-v2/etl/README.md)。聚合前裁剪历史、列和未显示模块可以减少搬运与渲染；没有同环境首屏计时与查询测量时，不给出速度提升百分比。

## 手机排版与明细

沿用源码中的 CSS 变量统一正文、辅助说明、次级标题、核心金额和行高；辅助文字优先可读，主标题克制。说明文字有空间时允许换行，券名完整展示，不为单行强行缩小字体。数据与单位分层，按钮触控高度至少44px。

四个周期同时驱动首屏明细入口、券转化入口和各自弹层标题。“昨天”在明细标题中写为“昨日”。每日明细以总额／堂食／外卖切换完整的一组金额、订单和客单；弹层 flex 容器限制高度，内部数据区滚动，表头 sticky。日期与星期分行，周末浅杏色。8周趋势日期拆行并保留完整周区间说明。顾客快照统一叫“近期堂食的顾客”，不随顶部周期变化。

新增二级详情与告警都放在原模块内部，不改变主页面章节顺序。页尾说明只用于业务分析，精确信息以财务口径为准，异常联系本组织支持人员；公开示例使用通用联系人。

## 会员跨店比较

采用固定近30天会员订单数÷可识别顾客订单数，按同分公司、同城市、同店型展示名次及中位数。它衡量识别订单中的会员渗透，不能当作复购率、获客能力或因果经营收益。

默认参评门槛为至少300单、至少21个有订单日期、顾客识别覆盖率至少80%，并检查缺失与口径冲突。识别订单超过对照POS订单的105%也应核验。参评不足的店展示原因；组内少于3家不排名；前后两个30天都符合条件时才显示占比变化。阈值应结合业务调整，不把低识别率判成低运营水平。

## 不依赖大模型的异常提示

会员集中订单先筛POS完成订单：单笔至少200元，且至少达到本店非会员客单价5倍。同一会员至少3笔、跨至少2天，合计至少1000元，且占会员金额至少20%才提示。优先展示金额最大的候选，同额重复与高额集中均可触发。前端仅接收聚合 JSON，不接收会员身份或订单号。

提示的支付类别来自数据原字段，不能把 POS 等同现金或认定操作者是员工、店长或加盟商。正常团餐、集中挂账也可能触发，需要小票和真实支付流水核验。指标保留原始数据，不自动扣减；警示不作为处罚依据。

汤底以近7天订单为分母，订单至少50笔、缺失至少50笔且识别覆盖低于50%时提示。堂食优先检查收银是否标准点选及商品映射；外卖检查商品到汤底映射。覆盖率缺失、非法或样本过小不触发。排行只代表已识别的汤底订单。

两类规则由 SQL 与普通前端条件执行。每天更新依赖上游抽取、ETL调度和成功产出，与大模型无关；部署后需单独观察一次自然触发成功，不能把手动运行当成自然运行。

## 券转化与核销关联

金额来源为整单日志与POS交叉校验。券种内按订单去重；跨券种叠券，每行可显示同一笔整单金额，但顶部总计必须独立按订单去重。实际折扣为有效订单实付合计÷原价合计×10，不能平均逐单折扣，也不能照抄券名称。

“每优惠1元对应实付”不是ROI或新增营收。整单优惠可能包含其他活动，不能称为单券净成本。券作支付时，日志可能实付等于原价、抵扣为0；未知的顾客现金支出和折扣成本不能据此记为0。

当前 SQL 将缺订单号／订单未找到统一列为 unmatched；非完成状态、券作支付、金额缺失或冲突另列。核销数仍展示，未知金额排除。只向前端补一个聚合JSON字段，无需额外订单级查询。

未匹配要继续往上游追：券使用状态→使用订单流水→交易日志→POS订单；必要时比对同店同顾客附近交易的实际券号。发现另一张已计金额的券时不能按相近时间补关联，否则会重复归因。详细排查与可确认边界见 [券订单关联排查](coupon-order-link-diagnosis.md)。

## 验证与公开范围

发布前检查四周期联动、换店、日明细三切片、冻结表头、券明细两切片、正常无警示／异常有警示／无核销空态。自动化检查覆盖叠券总计、加权折扣与未知金额；本地演示和线上生产验证是不同证据，不能互相替代。

公开内容只有脱敏后的前端源码、合成数据生成器、SQL模板和经验说明。不包含生产页面导出、账号配置、源样本、执行日志、会员标识、券号、订单号或带水印的生产截图。原页面与数据源应保留，先在隔离副本完成验证。
